# IOTA Train at Home v4.12.10 local safety fixset

This directory freezes the client-side changes tested against the public
`macrocosm-os/iota` v4.12.10 source. It does not change coordinator semantics
or modify the signed official desktop application. The combined artifact is a
local experimental patch, not an official Macrocosmos release.

The patch is intentionally version-locked. Do not apply it to a later tag
without rebasing and repeating the complete test gate.

Large ranged downloads retain verified bytes across transient disconnects and
request timeouts. Each retry requests only the unreceived suffix and validates
its exact `Content-Range`; gaps, overlaps, and full-object fallbacks fail closed.

## Included changes

1. Epoch-local cleanup and upload guard
   - carries epoch cleanup across a phase transition that occurs during the
     final merge submit;
   - resets stale P2P and training state before the next training epoch;
   - uses epoch-local optimization steps rather than a process-lifetime
     backward counter before uploading weights.
2. Registration/reset reconciliation
   - resets the local advertised status to `initializing` on re-registration;
   - repairs an existing own-registry entry whose status disagrees with the
     process state, while treating an absent entry as startup rather than
     false drift.
3. Bounded P2P status retry and rotation
   - removes the five-second outer cancellation that defeated the SDK retry
     policy;
   - limits and rotates background sends;
   - derives a final hard timeout beyond the SDK's complete retry budget;
   - cancels stale payloads and clears task/diagnostic state on empty targets,
     phase changes, re-registration/reset, and shutdown.
4. Faster phase-transition detection
   - performs one immediate local phase probe when the run-wide gate closes;
   - follows with a stable per-miner jittered cadence between three and five
     seconds, avoiding a fleet-wide two-second polling pulse;
   - propagates terminal phase and deregistration responses and bounds
     rate-limit retries.
5. HTTP connection pooling
   - reuses one worker-owned coordinator session;
   - reuses separate verified-TLS and local/minio S3 upload pools;
   - keeps explicit per-request upload timeouts;
   - closes all owned sessions during worker shutdown;
   - preserves caller ownership and cancellation behavior for borrowed
     sessions.
6. Headless registration attestation and queue evidence
   - uses the public signed native software-attestation helper when the pool
     worker is not mounted in the Electron host;
   - refuses to submit a reserved-run confirmation when the challenge,
     factory, or attestation payload is absent;
   - keeps the audited upstream pool entrypoint unchanged and adds a separate
     standalone entrypoint/subclass;
   - logs complete registration/queue/confirmation/challenge responses and
     writes a 0600 machine-readable transition journal without request bodies
     or authentication headers.
   - treats signed-host queue-state reporting as a bounded, detached observer,
     so an absent host capability cannot delay or reset authoritative
     coordinator registration polling;
   - forwards that optional observation only when the verified host advertises
     `register.queue_state`, otherwise recording an explicit unavailable
     outcome instead of retrying a protocol method the v3.7 host lacks;
   - exits with code 78 on deterministic native helper identity mismatch
     (native error code 15), preventing an unproductive registration loop.
7. Mounted-host registration-status compatibility
   - keeps the internal `training` literal unchanged for P2P peer routing;
   - maps that wider runtime state to the host's legal `registered` status;
   - preserves every legal registration status unchanged and rejects unknown
     values before contacting the signed host;
   - leaves detailed work lifecycle reporting on the independent
     `training.state` channel.
8. Deterministic Apple-MPS runtime
   - selects and validates MPS explicitly instead of silently falling back to
     CPU;
   - disables inherited MPS fast-math/prefer-Metal toggles for the qualified
     production path;
   - keeps CUDA/NVML-only diagnostics informational on Apple Silicon.
9. End-to-end numerical containment
   - validates shapes, dtypes, layouts, and finite values at P2P ingress,
     training boundaries, optimizer reconstruction, partition merging, and
     every upload boundary;
   - makes a non-finite gradient norm a hard error and clears poisoned
     gradients/state instead of allowing `optimizer.step()` to spread NaNs;
   - fails closed on empty or partial download, merge, and upload batches, and
     on finite-to-half cast overflow.
   - binds every partition, optimizer, pseudograd, merge, and upload payload to
     its expected layer/chunk descriptor, including legacy weight blobs, so a
     finite tensor from the wrong layer cannot pass validation;
   - retries only genuinely transient global-weight failures with a bounded
     three-attempt budget, while registration, phase, capacity, and numerical
     failures propagate immediately and retry exhaustion fails closed.
10. Epoch-local non-finite recovery
   - quarantines only the affected epoch and suppresses its training ticks,
     weight uploads, and partition submissions;
   - commits model and optimizer snapshots as one atomic, transaction-matched
     pair and ignores torn, stale, or mismatched snapshots;
   - resumes only in a later training phase after a bounded authoritative
     global pull validates finite and a clean snapshot commit succeeds;
   - never emits a success or credit marker merely because local recovery ran.
11. Activation-queue producer progress
   - preserves the existing bounded 100 ms idle polling behavior;
   - releases `_queue_lock` before that sleep so fetch, P2P-push, reset, and
     shutdown paths are not serialized behind an idle consumer;
   - preserves backward-first selection and cache-full forward behavior.
12. Detached outbound-forward saved-tensor release
   - keeps grad mode enabled so production-reachable MPS SDPA and RMSNorm
     dispatch and outputs remain bitwise identical to the current worker;
   - drops only tensors saved for a backward that this immediately-detached
     outbound helper never performs, with a tensor-free sentinel and an
     explicit fail-closed unpack error;
   - activates only when the model explicitly declares the current
     `quantize_activations=False` empty-state contract;
   - keeps quantized or unknown contracts on the original grad-enabled path,
     preserving their state list, and recomputes safely on that path if an
     allegedly empty-state model unexpectedly returns state;
   - restores outer saved-tensor hook scopes on success and model exceptions;
   - is backed by fresh-process exact-shape AB/BA qualification showing
     multi-gigabyte live-MPS allocation reductions without exceeding the
     predeclared 2% median latency-regression ceiling on head or body.
13. Global-weight download, merge, and memory liveness
   - validates ranged responses down to status, range, length, and streamed
     byte count, disables implicit content decompression, and retries only the
     failed range for bounded transient failures;
   - derives strict encoded and decoded bounds from the authoritative local
     tensor/partition shape, with a 512 MiB hard safety ceiling;
   - freezes compression flags for each full operation and fences downloaded
     data against run, layer, epoch, descriptor, and generation changes before
     commit;
   - uses progress-driven watchdogs so continuing transfers are not killed by
     a wall-clock timeout, while truly stalled work is cancelled without
     spawning a competing retry or orphan writer;
   - treats exhausted transient refreshes as retryable local liveness faults,
     preserving valid registration while authoritative deregistration still
     resets immediately;
   - exports Darwin physical-footprint availability and applies serialized,
     pressure-gated allocator relief only at quiescent cleanup boundaries;
   - removes blocking full cyclic collection from the deadline-critical merge
     upload pipeline, allowing each newly scheduled upload an immediate event-
     loop turn.
14. Accelerator/controller/upload process split
   - keeps wallet, attestation, coordinator, and P2P authority exclusively in
     the registered parent process;
   - builds deterministic pseudogradients and the exact weights blob in a
     short-lived spawned CPU worker bound to run/layer/epoch/generation;
   - validates child output by owner-only receipt, byte count, and SHA-256;
   - parks model and optimizer tensors on CPU and empties MPS before transfer,
     restoring them before the next global-weight pull;
   - transfers the immutable blob in a separate credential-free process using
     only presigned URLs, while signed completion/submission stays in parent;
   - fails closed on stale binding, tamper, non-finite input, crash, timeout,
     or malformed multipart metadata.
15. Registration-reservation recovery
   - binds each confirmation attempt to the exact coordinator reservation
     tuple `(queue_id, selected_run_id, reserved_until)`;
   - sends at most one confirmation POST for that tuple, so an ambiguous
     timeout or retryable response cannot replay a single-use attestation;
   - reconciles the same authoritative queue after an ambiguous response and
     accepts a resulting registration without re-attesting;
   - abandons an expired or superseded reservation and returns to queue
     polling instead of spinning or silently starting a second confirmation;
   - applies a one-second minimum reconciliation poll to prevent a malformed
     or zero-delay response from creating a tight coordinator loop.
16. Activation transport budget (`iota-v4.12.10-activation-transport-budget.patch`)
   - bounds outbound activation sends with a per-target transport budget and a
     dedicated sender so a slow peer cannot starve the rest of the fan-out.
17. Poisoned global-generation recovery
   (`iota-v4.12.10-poisoned-global-generation-recovery.patch`)
   - fingerprints a merged-partition generation whose shard repeatedly fails
     the cosine check, records the rejected descriptor and payload digest,
     quarantines that generation without deregistering, and retries only
     after the coordinator's epoch or descriptor changes.
18. Coordinator-contract liveness
   (`iota-v4.12.10-coordinator-contract-liveness.patch`)
   - restores upstream's limited cosine-only global-weight fallback (at least
     90% accepted shards) only after a prior valid global sync and outside
     fresh numerical recovery;
   - backs persistent invalid generations off from 60 seconds to 15 minutes;
   - reads the coordinator training gate through one in-flight request with a
     cached TTL, cancels and awaits gate/fetch/materialization tasks at epoch
     cleanup, and emits `TRAINING_PROGRESS` every 30 seconds.
19. Adaptive upload concurrency (`iota-v4.12.10-adaptive-upload-concurrency.patch`)
   - replaces the fixed sixteen-way multipart upload semaphore with a
     process-local limiter that measures the aggregate throughput implied by
     completed parts and keeps only as many parts in flight as can each finish
     within half of the fixed `S3_UPLOAD_TIMEOUT`;
   - halves the limit immediately when a part actually times out, never
     exceeds `S3_UPLOAD_MAX_CONCURRENCY`, and never drops below
     `S3_UPLOAD_MIN_CONCURRENCY` (default 2);
   - logs every adjustment with the observed aggregate rate so a saturated or
     shared uplink is visible in the worker log;
   - deliberately does not coordinate across hosts: two Macs uploading in the
     same merge window still share the uplink, each one simply stops
     wasting it on timed-out retries.
20. Single-connection peer fanout (`iota-v4.12.10-single-connection-peer-fanout.patch`)
   - makes the per-peer P2P request semaphore an operator knob; the default
     stays at upstream's 2 now that the SDK is pinned to 0.1.3 (iroh 0.98.1);
   - motivation: the SDK's embedded iroh 1.0.0 grows one contiguous native
     buffer without bound (n0-computer/iroh #4390, needs >= 2 paths per peer;
     fixed upstream in #4414 after the SDK build). Captured live on the Studio
     on 2026-09-10 (9 -> 41 GB in 6 min) and 2026-09-14 (22 -> 44 GB in 8 min),
     both at the epoch weight-upload/merge boundary on a healthy link;
   - `STRATA_P2P_MAX_CONCURRENT_PER_PEER` (clamped to 1..4) sets the limit;
     1 removes the >=2-connection precondition of the iroh 1.0.0 bug if a
     build ever embeds that SDK again; the effective limit is logged at init;
   - this is a mitigation of the trigger precondition, not a fix of iroh; the
     SDK ships wheels only, so the embedded iroh cannot be rebuilt locally.
21. Upload critical path (`iota-v4.12.10-upload-critical-path.patch`)
   - motivation: the coordinator moves a layer from `weights_uploading` to
     `merging_partitions` as soon as the last other miner has submitted; on
     2026-09-17 the Studio's 1 GB pseudo-gradient upload finished 5 s after
     that transition twice (run .7 epoch 311, run .6 epoch 233), each time
     the weights were rejected and the miner was deregistered into the
     registration waitlist. Every second between the state change and
     `submit_weights` is a second of that window;
   - starts the coordinator state notification + weights attestation
     challenge, the presigned-URL request (sized from the previous epoch's
     blob, verified against the real byte count and re-requested on a
     mismatch) and the upload worker's process start while the CPU worker is
     still building the blob, instead of serially after it;
   - a pre-spawned upload worker blocks in `_wait_for_job` until the parent
     publishes the job atomically; it exits on its own after the build
     timeout, the parent terminates it on any earlier failure, and a fresh
     worker is spawned if it is not alive at dispatch;
   - drops the two redundant full SHA-256 passes over the 1 GB artifact
     (parent pre-dispatch, child post-upload) that sat on the same critical
     path; the parent's post-build validation and the child's pre-upload
     digest check remain, and both sides verify the byte count;
   - `PHASE_WORKER_OVERLAP_CRITICAL_PATH=false` restores the serial order for
     A/B measurement; `PHASE_SPLIT_CRITICAL_PATH` and the extended
     `PHASE_SPLIT_UPLOAD_COMPLETE` log lines report build, submit, initiate
     and dispatch outcomes per epoch;
   - does not change the blob format, part layout, multipart concurrency or
     any coordinator contract; expected gain is roughly 8-12 s per epoch on
     the Studio, not a substitute for a faster uplink.

## Deliberately excluded

- Speculative attestation challenge prefetch or blind confirmation replay.
  The client now guarantees one confirmation POST per exact reservation and
  reconciles ambiguity, but it does not invent a coordinator-side durable
  idempotency receipt or reuse a challenge across reservations.
- Speculative multipart-init prefetch. The public API has no usable abort
  route or explicit cleanup/TTL contract for abandoned uploads.
- Stateless P2P cold-start exploration. It needs a one-outstanding-probe
  budget, acknowledgement feedback, and a network-wide rollout design.
- Event/condition activation wakeups. Detached materialization tasks can cross
  epoch reset and shutdown today; a wakeup design therefore requires
  generation fencing or cancel-and-await ownership plus full lifecycle tests.
  The shipped lock-release patch deliberately adds no wakeup state.
- Any claim of coordinator acceptance, validator credit, entitlement, or
  payout. Those remain separate external proof stages.

These exclusions are correctness boundaries, not abandoned ideas. They need
coordinator/API commitments before they are safe to activate.

22. Registry entry tolerance (`iota-v4.12.10-registry-entry-tolerance.patch`)
   - motivation: on 2026-09-21 07:09 local a peer in run 4.12.16.8 published a
     node-registry record with `node_id` as a list and `joined_at` as an
     ISO-8601 string; `ComputeNode(**entry)` raised a pydantic
     ValidationError out of `training_loop_tick`, the miner shut down and the
     Studio was offline for three hours before anyone noticed;
   - `all_nodes()` and `get_group()` now parse each record through
     `_parse_registry_entry`, which skips records the `ComputeNode` model
     rejects and logs one warning per node per five minutes instead of
     raising; own-record writes and every coordinator contract are unchanged;
   - unit tests: `src/miner/tests/test_registry_entry_tolerance.py`.

23. Registration run hint (`iota-v4.12.10-registration-run-hint.patch`)
   - motivation: on 2026-09-21 run 4.12.16.8 froze at epoch 320 for more than
     ten hours while the Studio's Bronze seat sat in `initializing`; the
     orchestrator picks the run server-side (`selected_run_id` in the queue
     status), but the attestation-challenge request already accepts a
     `run_id`, so this experiment asks whether a client-named run steers the
     initial assignment;
   - `subnet.registration_run_hint` reads an operator hint from
     `STRATA_IOTA_REGISTRATION_RUN_HINT` or, when unset, the owner-only file
     `~/Library/Application Support/STRATA/IOTA Worker/registration-run-hint.json`
     (`{"run_id": "4.12.16.7-tah"}`); a missing, symlinked, oversized or
     malformed hint means "no hint" and never raises;
   - `MinerAPIClient.request_attestation_challenge` uses the hint only for
     `action == "registration"` when no run was given, so queue confirmations
     keep the orchestrator's `selected_run_id`; `register_miner_request` adds
     `run_id` to the `/miner/register` body, logs
     `Registration run hint outcome: requested=… assigned=… (HONOURED|IGNORED)`
     after every registration, and after one HTTP 4xx (other than 429) on a
     hinted body sends the stock body for the rest of the session; every
     coordinator contract is otherwise unchanged and the pool miner bytecode
     is untouched;
   - unit tests: `shared/subnet/tests/test_registration_run_hint.py`.

### Patches that reached the chain without a write-up

Four patches were bound into the ordered chain, the manifest and every verifier
but were never described above. Recorded here on 2026-09-22 so the numbered
list is not mistaken for the whole chain; the numbering is left alone because
the digests and the ordered apply sequence depend on it.

- **Attestation pipeline** (`iota-v4.12.10-attestation-pipeline.patch`):
  `activation_publisher` collects an activation's attestation and notifies the
  orchestrator as a pipeline (`_collect_activation_attestation` feeding
  `_notify_after_attestation`) instead of serialising the two, so the
  notification waits on the pipelined attestation rather than a fresh one.

- **Post-ack dedup** (`iota-v4.12.10-post-ack-dedup.patch`): the P2P stack keeps
  a delivery-dedup ledger so a duplicate post-ack push is enqueued exactly once,
  forward and backward keys stay distinct, a full queue cannot poison the
  ledger, and an epoch drain clears it.
  Unit tests: `src/miner/tests/test_p2p_stack_routing.py`.
- **TensorOps GQA** (`iota-v4.12.10-tensorops-gqa.patch`): routes llama3
  grouped-query attention through the local Metal TensorOps runtime
  (`subnet/model/llama3/tensorops_runtime.py`, `_grouped_attention`), loading
  the kernel from the packaged asset root and falling back when it is absent or
  non-finite. This is the patch whose first production forward/backward the
  worker logs as `SN9 TensorOps first production … hit`.
- **Transport health routing** (`iota-v4.12.10-transport-health-routing.patch`):
  adds `miner/training/transport_health.py` (`PeerHealth`, `DeliveryOutcome`,
  `classify_generic_failure`, `may_reroute`) so activation delivery can reroute
  away from a peer that keeps failing, with the thresholds in `miner/settings.py`.

## Patch 21: return-aware forward routing (27 September 2026)

`iota-v4.12.10-return-aware-routing.patch` is the twenty-first ordered source
patch, applied last. Transport-health routing picks a forward peer by free
cache, delivery success and acknowledgement latency, but a peer can acknowledge
a push in a tenth of a second and then never return the backward. On layer 0
each such forward holds one of the 16 cache slots for the full cache timeout
(900 s; 600 s on the middle layer). The patch adds the missing signal: the time
until the matching backward arrives, or the full hold time when it expires.

- `TransportHealthRouter` records each acknowledged forward's peer
  (`note_forward_dispatched`), resolves it on backward arrival (`record_return`)
  or cache expiry (`record_expiry`), keeps a per-peer EWMA, and multiplies each
  candidate's score by `clamp((median_candidate_cost / peer_cost) ** 1.5, 0.2, 4.0)`.
  Peers with fewer than three resolved sends stay neutral; the 0.2 floor keeps
  slow peers sampled so a recovery is noticed; bookkeeping is capped at 8192
  pending ids.
- Hooks: the publisher notes acknowledged forwards, the activation queue
  reports a materialized backward, and the activation cache reports expiry. A
  failing hook is logged at debug level and never affects delivery or cleanup.
- Layer behaviour: layer 0 and the middle layer forward and learn; the last
  layer never forwards, so the router is unused and nothing changes there.
- Disable with `STRATA_SN9_RETURN_AWARE_ROUTING=0` (it is otherwise on whenever
  transport-health routing is on).

Evidence, from the Studio's own logs over 3–27 September (43,613 resolved
layer-0 sends on 11 days, 36,686 layer-1 sends on 10 days): a peer's cost in
one two-hour window predicts the next (rank correlation 0.67 on layer 0, 0.88 on
layer 1; the cheaper half cost 113 vs 216 slot-seconds per return next window on
layer 0 and 18 vs 42 on layer 1). Timeouts took 22% of layer-0 and 31% of
layer-1 slot time. Replaying the logs with this scoring, holding each peer at its
observed cost, gave 22% more returns per slot-second than what actually
happened on layer 0 and 62% on layer 1. The replay cannot see the capacity
signal the live router also uses, so the real gain is expected to be smaller;
on layer 1 it applies only to the ~32% of time spent waiting for free slots.
Tests: `src/miner/tests/test_return_aware_routing.py` (router weighting,
expiry cost, neutral new peers, floor/ceiling, disabled flag, bounded
bookkeeping, last layer, cache expiry callback and a failing callback), and
`test_transport_health.py`, which the build did not previously run, now runs in
both the build and `verify.sh`.

## Patch 23: upload straggler hedging (29 September 2026)

`iota-v4.12.10-upload-straggler-hedge.patch` is the twenty-third ordered source
patch, applied last. It changes `common/utils/s3_utils.py`, which both upload
paths use:
- weights, through `phase_worker.py`;
- merge partitions and optimizer state, through `miner_api_client.py`.

**What happened.** On 29 September at 01:32 the MacBook's first worker started
its epoch-38 weight upload: 97 parts of about 10 MB. All but one part finished
normally. Part 53 hung until the fixed 300 s request timeout, and its retry then
finished in about 3 s. The upload took 342 s instead of the usual 91–142 s.
`submit_weights` arrived about 18 s after the layer moved to
`merging_partitions`, so the epoch was rejected and the orchestrator removed the
worker from run 4.12.16.23.

**The fix.** `UploadStragglerHedge` watches each part PUT. Once a part has been
in flight longer than `4 × median` of the parts already finished, it starts a
second PUT of the same bytes to the same presigned URL and keeps whichever
finishes first. The other one is cancelled.
- The threshold is clamped to 15–90 s, and is 90 s until four parts have
  finished. It is re-checked every 2 s, because it tightens as more parts
  finish.
- Re-uploading an identical part number is valid in S3/R2 multipart uploads and
  yields the same ETag, so the complete call is unaffected.
- At most 25% of a blob's parts are duplicated.
- If both copies fail, the existing retry loop takes over. The retries, backoff,
  adaptive concurrency and 300 s timeout are unchanged.
- To disable it, set `S3_UPLOAD_HEDGE=0`. The tunables are
  `S3_UPLOAD_HEDGE_FACTOR`, `_MIN_SECONDS`, `_MAX_SECONDS`, `_MIN_SAMPLES` and
  `_BUDGET_FRACTION`.

**Replay against real logs.** The part-completion and part-failure lines of
every upload in the worker logs were replayed through the same decision.

## Patch 22: P2P endpoint recovery (27 September 2026)

`iota-v4.12.10-p2p-endpoint-recovery.patch` is the twenty-second ordered source
patch, applied last. On 27 September the MacBook's router lost its upstream for
about a minute (19:37; the Mac's interfaces stayed up, Tailscale logged
timeouts and DNS refusals). HTTP to the orchestrator recovered by itself, but
the in-process iroh endpoint never did: the last inbound `/peer/status` arrived
at 19:37:06, and after that every 30 minutes showed 0 successful and about 240
failed peer-status sends. The epoch-20 upload at 19:42 (work done before the
drop) was accepted; epoch 21 took no local steps, the upload was skipped as a
no-op, and the orchestrator removed the worker at 21:44 during
merging_partitions. `reset_miner_state` does not touch the P2P stack, so the
worker went back to the queue with the same dead endpoint.

- `miner/p2p/liveness.py`: `p2p_restart_reason` decides, and
  `recover_p2p_endpoint` acts. A rebuild needs all of: the endpoint older
  than the startup grace (180 s); no rebuild in the cooldown (300 s); at least
  6 peer-status sends failed since the last success; and both no inbound P2P
  message and no successful peer-status send for the stall window (180 s).
  Silence is measured from the endpoint's own start, never from before a
  rebuild. A miner with nobody to send to (queued, or alone in its layer)
  never accumulates failures and is never rebuilt.
- `P2PStack` records the last inbound message on every path (`/peer/status`
  before its filters, activation push, activation request) and gains
  `restart()`: stop, then start again from the same seed, so the node id and
  registry entry stay valid. The push queue and peer-status table are kept.
  A failed start is retried after 2, 5 and 10 s; if all fail, the stack is left
  cleanly stopped and the next liveness check tries again.
- After the rebuild the mesh re-registers peer address hints
  (`on_sender_restarted`), pulls, and pushes its own entry so peers learn the
  new relay URL and direct addresses. Registry errors are logged and left to
  the mesh's background sync. The re-registration is essential: a rebuilt
  sender starts with an empty address book (iroh public discovery is off, so
  it fails with `PeerAddressUnknownError`), and the mesh's routine sync skips
  peers it has already registered. Peer addresses go back at once; our own
  entry is re-published only after the new endpoint reports a home relay (up
  to 15 s). A fresh endpoint has none for a moment, and publishing then would
  replace a still-working relay hint with none, leaving NATed peers unable to
  reach us until a later sync.
- On a rebuild, return-aware routing (patch 21) drops its unresolved forwards
  without scoring them: backwards that could not reach us while our endpoint
  was dead measure our outage, not the peers.
- The miner counts peer-status send failures since the last success, and a
  watchdog task in `training_loop` checks every 30 s.
- Settings: `STRATA_SN9_P2P_LIVENESS_WATCHDOG` (default on; `0` disables).
  The mounted proxy launches the worker with a fixed environment and passes
  this switch and `STRATA_SN9_RETURN_AWARE_ROUTING` through only when the
  terminal that runs `mounted-proxy run` sets them to exactly `0` or `1`.
  STRATA's own session does not pass them, so the way back there is the
  previous STRATA build. Tunables (not passed through by the proxy):
  `P2P_LIVENESS_CHECK_INTERVAL_SECONDS`, `P2P_LIVENESS_STALL_SECONDS`,
  `P2P_LIVENESS_MIN_FAILED_SENDS`, `P2P_LIVENESS_RESTART_COOLDOWN_SECONDS`,
  `P2P_LIVENESS_STARTUP_GRACE_SECONDS`.

Tests: `src/miner/tests/test_p2p_endpoint_recovery.py` covers the decision
(dead, recent inbound, recent outbound, too few failures, grace, cooldown,
silence counted from the restart, disabled), `P2PStack.restart` (same seed and
node id, old endpoint closed, queue and peer table kept), inbound tracking on
all three paths, the recovery order and its tolerance of registry failures, and
the miner wiring (one rebuild, then cooldown; healthy endpoint untouched;
failure counter), start retries and a clean stop when every retry fails, and
the full recovery chain through the real `ElasticDeviceMesh` (the rebuilt
sender and activation sender get every peer's hints back; a routine sync alone
does not). The same 78 tests in the full miner suite fail on the
21-patch baseline and with this patch, all for reasons outside it; none are new.

Live check with the real iota_sdk (two stacks over the n0 relay, 27

## Patch 24: registration admission recovery (29 September 2026)

`iota-v4.12.10-registration-admission-recovery.patch` is the twenty-fourth
ordered source patch, applied last. It changes the registration path in
`subnet/miner_api_client.py` and `subnet/common_api_client.py`, and overrides
the pool miner's compiled `register_loop` in `miner/standalone_pool.py`.
`tests/src/miner/tests/test_registration_retry_backoff.py` is a new fixset
overlay test (it needs the extracted pool bytecode, like the headless
attestation test).

**What happened.** A log review of every registration journal on the Studio,
both MacBook workers and the Mac mini (2–29 September) found 23 reservations
since 18 September. Only 8 became admissions:
- 10 failed with `invalid_attestation_challenge` after the coordinator had
  accepted the confirmation. That is server-side and nothing here changes it.
- 2 were lost after the confirmation POST got HTTP 500, both on the Mac mini
  (29 September 12:15:28 and 15:55:32, run 4.12.16.23). The 500s left 39 s and
  52 s of the ~90 s reservation. The coordinator kept answering `confirming`,
  "Fresh registration confirmation is required." for the same reservation, but
  the client only polled until it expired and the entry was dropped.
- 1 was skipped because it was first seen with 10.5 s left, the challenge took
  7.2 s, and the 5 s safety budget refused to confirm with ~3 s left.
- 6 queue entries expired for inactivity: the coordinator drops an entry after
  about 3 minutes without a successful status poll, and one failed poll could
  take 92–124 s (3 attempts × 40 s).
- The upstream `register_loop` retried every failure after a flat 10 s, which
  re-posted `/miner/register` with a fresh challenge 36 times in 9 minutes on
  6 September while the host signer was failing.

The one-confirmation-per-reservation rule came from patch 15, which stopped an
ambiguous response from replaying a single-use attestation. Upstream v4.12.10
re-sent the confirmation up to three times.

**The fix.**
- A confirmation answered with HTTP 500 or 503 (a completed response, not a lost
  one) is followed by a status reconciliation. If the same reservation is still
  `confirming` with `confirmation_required`, the client requests a NEW
  challenge and attestation and confirms once more: at most two confirmations
  per reservation, never the same attestation twice. 502/504/408/425 stay
  ambiguous and 429 is never retried, as before.
- An attestation that fails or returns nothing while the reservation is open
  (for example `request_attestation_challenge` swallowing a server error) is
  retried once with a fresh challenge instead of abandoning the reservation.
  The reservation deadline is published to `request_attestation_challenge`
  through a context variable (same task, so an identity-mismatch
  `SystemExit(78)` still propagates), which bounds the confirmation challenge
  to one attempt that cannot outlive the reservation.
- The safety budget drops from 5 s to 1.5 s: an unconfirmed reservation is lost
  anyway, so the margin only has to cover the confirmation request.
- Status polls are one attempt with a 20 s timeout; the existing outer backoff
  keeps the queue id. Polls are spaced start-to-start, so a slow response
  (p99 25–35 s) no longer delays noticing a reservation. The request rate does
  not go up.
- `HeadlessPoolMiner.register_loop` keeps the upstream outcomes (spec mismatch
  fatal; `initializing` retried every 10 s, the seat-reclaim path) but backs
  off 10 → 20 → … → 300 s while registration keeps failing within 120 s. A
  failure that ends a long queue wait still rejoins after 10 s.
- `CommonAPIClient.orchestrator_request` gains an optional `timeout_seconds`.

**Replay.** The audit's fake-clock replay of both Mac mini incidents: without
the patch, one confirmation and then "Registration queue entry expired."; with
it, a second confirmation with a fresh attestation about 24 s after the
reservation was seen, and the worker registers with 25–40 s to spare. If the
second confirmation also gets 500, it stops at two confirmations after six
status polls.

**Tests.** `shared/subnet/tests/test_registration_admission_recovery.py` ships
inside the patch: re-attest after 500, bounded at two, no re-attest for
502/504/408/429, no re-attest once the coordinator committed or the budget is
spent, attestation retried once then failing closed, the challenge bounded by
the reservation, `SystemExit` propagation, start-to-start polling, the
single-attempt 20 s status poll and the per-call timeout. One
`test_registration_reservation_recovery.py` fixture moved its fake deadline
into the future (a past deadline with a "has budget" answer cannot happen).
The common, miner and subnet suites fail the same pre-existing tests before
and after the patch; none are new.

**Not changed.** `invalid_attestation_challenge` after a successful confirmation
(10 of 23 reservations, 7 of MacBook worker 2's 8) happens on the coordinator.
A setup error right after admission still exits the worker with no automatic
restart; that belongs to the STRATA supervisor and is tracked separately.

## Patch 25: structured event journal (29 September 2026)

`iota-v4.12.10-structured-event-journal.patch` is the twenty-fifth ordered
source patch, applied last. It adds `common/utils/strata_event_journal.py` and
seven one-line `emit()` calls in `subnet/common_api_client.py`,
`miner/new_miner.py` and `miner/training/training.py`, each placed right after
the log call it mirrors, under the same conditions. Its test,
`shared/subnet/tests/test_strata_event_journal.py`, ships inside the patch.

**Why.** The STRATA app derived every worker fact by scraping free-text log
lines: roughly 30 message types and 25 facts, matched by substring and regex.
Wording is upstream's and can change in any release. The heartbeat response in
the text log is also truncated to 100 characters, so a coordinator that adds
fields would silently stop being recognised. Parsing that text was most of the
app's CPU cost; see `Research/STRATA_IDLE_CPU_OBSERVABILITY_READERS_2026-09-29.md`
and `reports/Low CPU incremental log parsing.md`.

**What the worker writes.** The mounted proxy (`mounted_proxyctl.py`, a
control-surface change) creates `events-<session>.jsonl` next to the
registration journal (`O_EXCL`, 0600). It passes the path as
`STRATA_IOTA_EVENT_JOURNAL` and records it as `evidence_paths.event_journal`
in the session receipt. The worker appends one sorted-key JSON object per
event with `schema_version` 1, `wall_time` (UTC), `monotonic_seconds`,
`event` and typed fields. The write path copies the registration journal's:
`O_APPEND|O_NOFOLLOW|O_CLOEXEC`, `fchmod 0600`, one `os.write`, strings
bounded to 2 KiB and records to 64 KiB, NaN written as null. Without the
variable every call is a no-op. A failure is logged at most once a minute and
never changes worker behaviour.

| event | emitted next to | fields |
|---|---|---|
| `heartbeat_response` | "Successfully completed request to /miner/heartbeat…" (every HTTP 200, including semantic failures) | `path`, complete `response` |
| `registered` | "registered successfully in layer … on training epoch …" | `layer`, `epoch` |
| `registration_started` | "Attempting to join registration waitlist" | – |
| `kicked` | "appears to have been kicked during active work" | `phase`, `run_id`, `layer`, `source`, `error` |
| `reset` | "Resetting miner entire state!" | – |
| `forward_complete` / `backward_complete` | "FORWARD complete" / "BACKWARD complete" | `layer`, `activation_id` |
| `training_progress` | the `TRAINING_PROGRESS` marker (patch 15) | `level`, exact `message`, `run_id`, `layer`, `fields` |

Each of those messages has exactly one emission site in the patched tree
(checked case-insensitively), so every fact is emitted once. Optimizer steps,
weights upload/submit/merge, activation transport, GPU and peer telemetry are
logged from several sites each and stay text-derived for now.

**What the app does** (`BittensorTAHWorkerEventJournal.swift`). For a session
whose receipt names the journal at exactly `root/events-<session>.jsonl`, and
where that is an owner-only regular file, the app reads it as part of the same
mounted-worker stream as the text log. The epoch ledger attributes evidence
per stream, so it has to be the same one. Each record is rendered to one fixed
canonical log line and parsed and redacted like any other worker record. The
text-log lines the journal replaces are dropped for that session: the covered
lifecycle events, every heartbeat response line and every `TRAINING_PROGRESS`
line. `BittensorTAHWorkerEventJournalTests` checks that such a session
produces the same lifecycle counts, heartbeat attempts, derived state, epoch
ledger rows, telemetry and progress marker as a text-only session of the same
activity. A mutant that stops dropping the text lines fails it. Workers
without patch 25 have no `event_journal` and stay entirely on text parsing.

## Patch 31: activation challenge retry (1 October 2026)

`iota-v4.12.10-activation-challenge-retry.patch` is the thirty-first ordered
source patch, applied last. It changes `miner/training/activation_publisher.py`.

**What happened.** Each activation is reported with `POST /miner/submit_activation`,
which carries an attestation over a fresh single-use challenge. The coordinator
rejects a growing share of these reports with `400 {"detail":"no_cached_challenge_found"}`:
about 5% in the long 22 September Studio session, 18% on 30 September and 20% on
1 October, the same on the Studio and the Mac mini. The activation was computed
and delivered to its peer, but the coordinator never recorded it, and the worker
only logged "Failed to notify orchestrator of activation …".

Pairing each report with its attestation (the `upload_activation` and
`submit_activation` timer records, by activation id, Studio 2,608 reports and
mini 777):
- even a challenge under 2 s old fails 18-26% of the time, so the coordinator
  loses challenges it has just issued;
- older challenges fail more (41-78% at 8-30 s), and slow challenge issuance
  goes with failure, so coordinator load makes it worse.

One example: the challenge was requested at 12:09:11, issued 8.4 s later, and the
report was rejected at 12:09:22, about 2.5 s after it arrived.

**The fix.** When `submit_activation` returns 400 with `no_cached_challenge_found`
or `attestation_required`, the publisher collects a fresh challenge and
attestation and sends the same report again, at most twice.
- Any other status or detail is not retried, and the final failure is logged as
  before.
- With attestation turned off by the run flags, nothing is retried.
- A 400 means the coordinator rejected the report before recording it, so a
  resend cannot count an activation twice.
- Retries log `ACTIVATION_CHALLENGE_RETRY`, and a report that succeeds after a
  retry logs `ACTIVATION_CHALLENGE_RETRY_OK`.

If a fresh challenge succeeds about 80% of the time, two retries leave about 1%
of reports unrecorded instead of 20%.

**Tests.** `src/miner/tests/test_activation_challenge_retry.py` ships inside the
patch (6 tests):
- only the two named 400 details count as challenge misses;
- a miss resends the same activation with a fresh attestation;
- retries stop after two;
- other errors are not retried;
- nothing is retried with attestation off;
- a first-time success collects no extra attestation.

They fail on the previous code. The miner suite fails the same 77 pre-existing
tests before and after.

## Patch 36: merge stall bound (4 October 2026)

`iota-v4.12.10-merge-stall-bound.patch` is the thirty-fifth ordered source
patch, applied last. It changes:
- `miner/new_miner.py` (`merge_partitions`, `_await_staged_merge_uploads`,
  `_collect_attestation_payload`)
- `miner/settings.py`, `common/settings.py`
- `subnet/common_api_client.py` (`orchestrator_request`)
- `miner/utils/timer_logger.py`
- `miner/utils/utils.py` (`_initiate_and_upload_blob`), `common/utils/s3_utils.py`
- new `common/utils/strata_progress.py`

**What happened.** On 4 October, during the MacBook's epoch 81 → 82 merge,
`complete_multipart_upload` (11:26:35) and two `initiate_blob_upload` steps
never returned. `merge_partitions` waited in `asyncio.gather(*upload_tasks)`
for 58 minutes although each coordinator request carries a 40 s × 3 aiohttp
timeout; the event loop stayed alive, but the main loop sent no heartbeat until
the process was restarted, which cost epoch 82 (research note, section 4). Why
no timeout fired was not determined. The fix does not depend on it.

**1. Progress-aware stall bound in `merge_partitions`.**
- The final wait for the staged uploads replaces the gather with a loop over
  `asyncio.wait(..., FIRST_COMPLETED)`. The first failed upload still fails the
  merge at once, as before.
- Progress is tracked by `strata_progress`: a tracker bound with a context
  variable inside each upload task, so only the merge's own calls count, never
  background traffic such as `get_run_config`. Marks:
  - each finished S3 part PUT, a patch-23 hedged duplicate included (`s3_part`);
  - each coordinator response, any status (`coordinator_response`);
  - each blob initiated, uploaded and completed, and each upload batch done;
  - attestation completion (`attestation_ready`; patch 29's slow attestation).
- The clock restarts when the final wait begins, so download and merge time
  between uploads never counts as a stall.
- After `MERGE_UPLOAD_STALL_SECONDS` (240 s) without progress:
  - `MERGE_UPLOAD_ABANDONED stage=… pending=… stalled_s=… total=… last_progress=… run=… layer=… epoch=…`
    is logged and a `merge_upload_abandoned` journal event written;
  - `MergeUploadStalled` (a `WeightPartitionException`) is raised, which the
    training loop already handles with `continue`;
  - the pending tasks are cancelled and given at most
    `MERGE_UPLOAD_CANCEL_GRACE_SECONDS` (5 s); a task that ignores its
    cancellation is detached and logged as `MERGE_UPLOAD_CANCEL_UNACKNOWLEDGED`.
    The same bounded cleanup now applies to every merge failure and
    cancellation; it used to be an unbounded gather.
- `submit_batch`, the protocol commit point, is never reached after an
  abandon, and the hung `complete_multipart_upload` is never retried by the
  merge; at worst an orphaned multipart upload is left for the coordinator.
- While waiting, `MERGE_UPLOAD_SLOW pending=… no_progress_s=… waiting_on=…`
  is logged at most once a minute once 60 s pass without progress.
- As after any merge failure today, the loop re-enters the merge on the next
  tick while the layer is still merging, with fresh uploads.

**Threshold check (240 s).** Logs from 448 merges on four Macs (Studio
09-03 → 10-03, MacBook 09-05 → 10-04, guru-mini 10-01 → 10-04, lurus-mini
10-03 → 10-04), with millisecond part-level lines:
- longest no-progress gap while an upload or a merge coordinator request was
  pending, in 362 healthy merges: p50 6.0 s, p90 14.9 s, p99 32.7 s, max 41.9 s
  (a slow attestation challenge followed by a retry); late-submit merges max
  41.4 s;
- longest clean partition-part PUT inside a merge: 48.0 s; no hedge ever fired
  inside a merge; partition blobs have 3 parts;
- weights uploads after the patch-23 hedge: max gap 32.4 s; before it, single
  300 s part timeouts produced 230–270 s gaps (the 09-29 incident was 233 s),
  which the hedge removes (replayed: the duplicate PUT fires at about 56 s);
- the 10-04 hang had 3,453 s without merge progress; the bound fires at 240 s.
Counting every gap including download time between uploads, healthy merges
reach 117 s, which is why the clock only runs during the final wait. If a
part's hedged duplicate also hangs, 240 s abandons the merge before the 300 s
S3 timeout would have retried it; that never happened in the 448 merges.

**2. Per-attempt deadline in `orchestrator_request`.**
- Each attempt runs as its own task under a deadline of its aiohttp timeout
  plus `ORCHESTRATOR_REQUEST_DEADLINE_SLACK_SECONDS` (5 s), independent of
  aiohttp's timer. A plain `async_timeout` block is not enough: it delivers one
  cancellation, and an attempt that swallows it would still hang.
- On expiry the attempt is cancelled and given
  `ORCHESTRATOR_REQUEST_CANCEL_GRACE_SECONDS` (2 s), then detached if it still
  runs (`ORCHESTRATOR_REQUEST_CANCEL_UNACKNOWLEDGED`). It logs
  `ORCHESTRATOR_REQUEST_DEADLINE path=… attempt=… deadline_s=… detached=…` and
  is treated like a timeout: the same retry and the same final
  `RateLimitException` as today.
- A cancellation of the caller cancels the attempt (bounded by the same grace)
  and propagates; it is never turned into a retry.

**3. Fire-and-forget telemetry.** `TimerLoggerMiner` posts its start, end and
count events to the visualization API as background tasks, at most 32 in
flight; a new event is dropped when 32 are still running. Nothing awaited the
post's result, so nothing depends on it. Tasks of a closed event loop are
pruned, and `cancel_pending_telemetry()` cancels the rest; asyncio's own
shutdown also cancels them, and each post keeps its 2 s httpx timeout.

**Tests.** `src/miner/tests/test_merge_stall_bound.py` (15 tests) ships inside
the patch:
- an upload awaiting a never-set event makes `merge_partitions` raise within
  the stall window, never call `submit_batch`, leave no pending task, and write
  one `MERGE_UPLOAD_ABANDONED` line and journal event;
- a slow upload that marks progress every 0.1 s (1.2 s against a 0.3 s bound)
  completes and submits;
- an upload that swallows its cancellation cannot hold the merge;
- a failed upload still fails fast;
- part PUTs and attestation mark progress; marks reach only the bound tracker;
- an `orchestrator_request` whose request hangs and swallows one
  `CancelledError` still returns control through the deadline, twice, then
  raises like a timeout; a hung first attempt is retried and succeeds;
- caller cancellation propagates without a retry, also when the request
  swallows it;
- the telemetry stays bounded at 32 and never blocks, and frees its slots.
Run against the previous code (with only the new helper module and settings
present so the file imports), 10 of the 15 fail, three by hanging. The five
that pass are the two settings checks, the helper-module test, and the two
behaviours that must not change (a progressing upload completes, caller
cancellation propagates). The miner suite fails the same 77 pre-existing tests
before and after.

**What happened.** On 5 October at 08:38:46 STRATA's memory guard stopped

the 20.0 GB cap (rss 10.4 GB)". The worker had just submitted its run

**Cause.** After the weights upload the compute plane is parked: the model and
the AdamW state (bf16, 1.01e9 elements, 1.89 GiB) sit on the CPU. The upload then
- concatenated a second full copy of the state (`flatten_optimizer_state`,
  `torch.cat`, +1.89 GiB), and
- ran `check_for_nans_and_infs` over it: `torch.isnan(t).sum()` makes a
  0.94 GiB bool mask and then a 7.5 GiB int64 copy for the sum, and
  `torch.isinf(t)` adds a 1.89 GiB `abs` copy. Measured on 1.01e9 bf16
  elements: isnan +8.5 GiB, isinf +10.4 GiB, isfinite +4.7 GiB at peak.
Replayed with the build-138 code on an L0-sized state, parked from MPS, the
footprint rose 15.3 GiB above the parked baseline for 4 to 6 s. On guru the
parked baseline was 14.3 GB.

**1. Bounded finite checks.** `check_for_nans_and_infs`,
`first_nonfinite_tensor_entry` and the phase worker's `_require_finite` scan
tensors larger than `FINITE_CHECK_CHUNK_ELEMENTS` (2^24) chunk by chunk and count
with `count_nonzero`. Counts, the first bad index, NaN-before-Inf order, log
lines and exception types are unchanged, and tensors at or below one chunk take
the original single call. Peak extra memory is about 80 MB whatever the tensor
size. Every caller benefits: the weights check before the build
(`require_finite_tensor` on the 0.94 GiB weights, about 2.4 GiB before), the
CPU build child, warm-up weight validation and the legacy upload path.

**2. Streamed optimizer-state blob.** `upload_optimizer_state_blob` writes the
blob to `phase-spool/optimizer-state-*/optimizer-state.blob` (0700 directory,
0600 file), one optimizer tensor at a time, then uploads it from a read-only
mmap through the same `_initiate_and_upload_blob` path as before (same
multipart layout, patch 23 hedging, patch 36 progress marks, patch 27 mmap
close). The tensors, order, bf16 conversion and finite checks come from the
same iterator `flatten_optimizer_state` uses, and the header and trailer from
the same `weights_blob_envelope` as `build_weights_blob`, so the file is
byte-identical to the in-memory blob. File-backed pages are not part of the
physical footprint the guard measures. Details:
- runs synchronously like the flatten it replaces, so nothing else touches
  the optimizer while it is written; no fsync (the file is read back from the
  page cache and deleted);
- logs `OPTIMIZER_STATE_SPOOLED bytes=… elements=… sha256=… seconds=… mode=mmap`
  and keeps the `_log_upload_ram` tags (`upload_weights_blob_entry`,
  `after_nan_inf_check`, `after_build_weights_blob`) for log continuity;
- falls back to the previous in-memory build (`OPTIMIZER_STATE_SPOOL_FALLBACK`)
  on any `OSError`, including less free space than the blob plus 2 GiB;
- removes its directory after the upload, failed or not; a directory left by
  a killed process is removed by the next spooled upload after an hour;
- `OPTIMIZER_STATE_SPOOL_ENABLED=false` restores the in-memory build (the
  finite checks stay bounded).
A non-finite or empty state fails exactly as before (same `NanInfException`
message, same `ValueError`), which the caller still treats as non-fatal.

**Measured** on the Studio with the real worker code, an L0-sized AdamW state
(embedding 128256x2048 plus four Llama-3.2-1B layers, 1.01e9 bf16 elements)
created on MPS and parked, uploaded through `upload_parts` to a local multipart
server in another process, peak footprint above the parked baseline:

| Path | Peak extra footprint | Time over baseline +2 GiB | Wall time |
|---|---|---|---|
| build 138 | 15.3 GiB | 4.3–5.9 s | 4.2–5.8 s |
| patch 37, spool off (bounded checks only) | 4.0–4.1 GiB | 1.5 s | 1.9 s |
| patch 37 (spool) | 2.1–2.2 GiB | 1.2–1.3 s | 2.6 s |

All three sent 194 parts, 2,023,817,405 bytes, with the same per-part SHA-256
chain. About 1.9 GiB of the remaining 2.1 GiB is the parked state itself:
pages copied from MPS are charged to the footprint only once the CPU reads
them, and every path has to read them.

**Tests.** `src/miner/tests/test_optimizer_state_spool.py` (48 tests) ships

- the checks never touch more than one chunk (`torch.isnan`/`isinf`/`isfinite`

## Patch 38: bench escape (10 October 2026)

`iota-v4.12.10-bench-escape.patch` is the thirty-seventh ordered source patch.
It changes `miner/new_miner.py`, `miner/utils/utils.py` (new
`extend_speedtest_cache`) and `miner/settings.py`.

**Why.** Since 4 October the orchestrator no longer lifts a miner that
registered mid-epoch (status `initializing`) at the next epoch flip; a
registration that lands in the first minutes of the layer's training phase is
still admitted as `idle`.

**What it does.**
- At the first training tick of an epoch, before the global-weight download,
  `_maybe_escape_bench` runs only when the last known status is
  `initializing`. A fresh heartbeat then decides: it must report
  `initializing`, phase training and an epoch later than the one the miner
  registered in. It runs at most once per epoch.
- The escape re-registers in place (no model rebuild, no reset backoff), up to
  `BENCH_ESCAPE_REGISTER_ATTEMPTS` (3) times, `BENCH_ESCAPE_RETRY_SECONDS` (5 s)
  apart. If every attempt fails, or the registration returns a different run or
  layer, it raises `MinerResetException` and the existing full reset takes over.
- Before registering it reuses an in-memory bandwidth measurement up to
  `BENCH_ESCAPE_SPEEDTEST_MAX_AGE_SEC` (6 h) old instead of running the speed
  test inside the admission window; it never invents or shortens a measurement.
- After `BENCH_ESCAPE_MAX_CONSECUTIVE` (3) escapes in a row that still come back
  `initializing` it stops until a registration comes back working.
- The reset backoff counter is cleared once the miner is registered and synced
  to the epoch's global weights (the clear after `training_phase.run()` was
  never reached).
- Logs `BENCH_ESCAPE`, `BENCH_ESCAPE_RETRY`, `BENCH_ESCAPE_DONE`; journal events
  `bench_escape_started`, `bench_escape_failed`, `bench_escape_moved`,
  `bench_escape_finished`. `STRATA_SN9_BENCH_ESCAPE=false` restores the old
  behaviour.

**Tests.** `src/miner/tests/test_bench_escape.py` (19 test functions) ships
inside the patch.

## Patch 42: deadline drop notify (10 October 2026)

`iota-v4.12.10-deadline-drop-notify.patch` is the thirty-eighth ordered source

## Patch 39: status freshness and slot reclaim (10 October 2026)

`iota-v4.12.10-status-freshness-and-slot-reclaim.patch` is the fortieth ordered
source patch. It changes `miner/training/transport_health.py`,
`miner/training/activation_cache.py`, `miner/training/training.py` and
`miner/settings.py`.

- **Status freshness.** A received peer status never expired, so a peer that
  stopped messaging us kept attracting forwards that never came back. Forward
  routing now prefers peers whose last status is at most
  `STRATA_SN9_STATUS_FRESHNESS_SECONDS` (900 s) old, or that returned at least
  2 backwards in the last 300 s. If no candidate qualifies, routing is
  unchanged. 0 disables the gate.
- **Stale-slot reclaim (layer 0 only).** When the activation cache is full and
  `cleanup()` found nothing timed out, the oldest slot is freed once it is older
  than both 450 s and the 98th percentile of observed return times, and only
  after 50 returns were observed. Logged as `STALE_SLOT_RECLAIM`; the expiry is
  recorded for return-aware routing. `STRATA_SN9_STALE_SLOT_RECLAIM=false`
  disables it.

**Tests.** `src/miner/tests/test_status_freshness_and_reclaim.py`
(12 test functions) ships inside the patch.

## Patch 40: training gate grace (10 October 2026)

`iota-v4.12.10-training-gate-grace.patch` is the forty-first ordered source
patch. It changes `miner/training/activation_queue.py` and `miner/settings.py`.

- The run-wide training gate is refreshed about every second, but a reply only
  counted for its 2 s TTL, so about 40% of ticks saw an expired answer and
  paused consumption although the orchestrator answered True more than 99% of
  the time. A True answer now stays usable for
  `STRATA_SN9_TRAINING_GATE_GRACE_SECONDS` (6 s) while a refresh is in flight,
  and a failed refresh keeps the last answer for the same window. A False
  answer still closes the gate at once; phase and registration errors still
  abort. 0 restores the old rule.
- Transient `get_activations` failures no longer end the layer-0 fetcher (which
  cleared its queues): it retries with a 2-5 s jittered backoff, draining
  backwards that already arrived, and fails as before after
  `STRATA_SN9_LAYER0_FETCH_MAX_ERRORS` (20) consecutive errors. Logged as
  `LAYER0_FETCH_RETRY`.

**Tests.** `src/miner/tests/test_training_gate_grace.py` (9 test functions)
ships inside the patch; one test in
`src/miner/tests/test_training_progress_liveness.py` pins the grace to 0 to
keep checking the original rule.

## Patch 43: DNS serve stale (10 October 2026)

`iota-v4.12.10-dns-serve-stale.patch` is the forty-second ordered source patch,
applied last. It adds `miner/utils/dns_fallback.py` and changes
`miner/standalone_pool.py` and `miner/settings.py`.

On 9 October the Studio's only resolver failed for 12 minutes inside an epoch's
weight-upload window; about 975 orchestrator requests failed on

## Patch 44: node-control heartbeat (10 October 2026)

`iota-v4.12.10-node-control-heartbeat.patch` is the forty-third ordered source
patch, applied last (sha256
`58219792c1f38f19e77f08676622f2523c08639869129b2ee813e650ce02ce1e`). It changes
`miner/utils/node_protocol_control_api.py` and `miner/settings.py`.

Upstream, the worker's node-control server pinged the host every 10 s and
closed the connection with 1011 when the last pong was more than 20 s old. It
checked right after sending the next ping, so one pong delayed by about 10 s
was enough. On the Studio, at a load around 110 on 16 cores, that closed the
verified relay 11 times in five days. The server no longer closes the host
connection after one delayed pong:

- Any frame from the host counts as alive, not only a pong.
- The timeout is `STRATA_SN9_NODE_CONTROL_PING_TIMEOUT_SECONDS` (60 s), bounded
  to 20-300 s. 20 restores the upstream limit.
- A check is skipped when the worker's own event loop overslept (the sleep
  between pings ran more than 5 s long), because frames the host sent in the
  meantime are still unread. It is logged as `NODE_CONTROL_PING_OVERSLEPT`; a
  real silence is logged as `NODE_CONTROL_HOST_SILENT` before the 1011 close.

**Tests.** `src/miner/tests/test_node_control_heartbeat.py` (5 test functions)
ships inside the patch.

## Patch 45: run avoid and emergency leave (11 October 2026)

`iota-v4.12.10-run-avoid.patch` is the forty-fourth ordered source patch,
applied last (sha256
`6ddd6df434e9a4df8ade62e2156370b987acf656dd499ae0b97d1a7e45d7dedf`). It adds
`subnet/registration_run_avoid.py` and `miner/utils/emergency_leave.py` and
changes `subnet/miner_api_client.py`, `miner/new_miner.py` and
`miner/standalone_pool.py`.

The orchestrator picks a miner's run, and nothing in the protocol leaves one.
After our TensorOps kernel corrupted run .24 (see
`../SN9_RUN24_CORRUPTION_INCIDENT_2026-10-11.md`), the M5 Macs had to stay out
of it.

- **Run avoid.** The supervisor passes the app's avoid list as
  `STRATA_SN9_RUN_AVOID` (comma-separated run ids).
  - A reservation offered in an avoided run is never attested or confirmed. The
    worker logs `RUN_AVOID_DECLINE` and the journal event
    `registration_run_declined`.
  - The worker waits for the reservation to expire, then registers again after
    10 s. After more than 6 declines in 24 h it waits an hour instead.
  - If the orchestrator returns a seat in an avoided run directly (the hotkey is
    still seated there), the worker does not train. It logs `RUN_AVOID_SEATED`
    and checks again every 5 minutes, so the seat lapses at that run's next
    upload window.
  - The production registration loop (`HeadlessPoolMiner.register_loop`) waits
    these out without counting them as failures.
- **Emergency leave.** The app arms it by writing `emergency-leave.json`
  (`{"schema_version": 1, "armed": true, "run_id": ...}`, owner-only). The
  supervisor passes its path as `STRATA_SN9_EMERGENCY_LEAVE_FILE`, and the
  worker re-reads it at every weight-upload window.
  - While armed for the run the worker is in, it skips that epoch's weight
    upload (`EMERGENCY_LEAVE_SKIP_UPLOAD`, journal
    `emergency_leave_skipped_upload`) so the orchestrator removes it at the
    epoch boundary. It keeps merging the partitions it was assigned.
  - When the removal shows up (the miner is no longer registered in that run),
    or the miner registers in another run, the file is rewritten with
    `"armed": false` and the outcome `kicked` or `left-run`. That turns the
    switch off. The run is then avoided in-process for 24 h, because the seat it
    freed is the first one the queue would hand back.
  - In-process bench escape (patch 38) and the external bench guard (v7) stay
    out while it is armed.
  - Missing uploads have cost a tier before (Bronze to Iron on 2026-09-18,
    restored two days later), so the app asks for confirmation.
- The patch also fixes an environment-dependent test from patch 36: the merge
  timers posted telemetry to the local visualization API. On a Mac where a live
  worker listens on that port, the connection attempt outlived the test and
  `test_hung_upload_is_abandoned_within_the_stall_window` failed. It failed
  clean worker builds on the MacBook and the Studio on 2026-10-11. That test now
  sends no telemetry.

**Tests.** `shared/subnet/tests/test_registration_run_avoid.py` (8 tests) and
`src/miner/tests/test_emergency_leave.py` (12 tests) ship inside the patch.

## Patch 46: TensorOps GQA v2 (11 October 2026)

`iota-v4.12.10-tensorops-gqa-v2.patch` is the forty-fifth ordered source patch,
applied last (sha256
`054f41988fd4745b030f77238788f731e36cd50e884ff7d47b27b7bbaaeb9010`). It changes
`subnet/model/llama3/tensorops_runtime.py` and `subnet/model/llama3/modules.py`.
It ships `shared/subnet/tests/test_tensorops_runtime.py`, 30 tests including one
real-kernel test.

**Why v1 was wrong on M5.** The v1 kernel (patch "tensorops-gqa") converted the
fp32 score tile straight into the left operand of the next matmul. It never
checked `is_compatible_as_left_input()`, which is 0 on Apple M5, where 896 of
1,024 elements landed at the wrong coordinate.

**The v2 kernels.** The kernel sources in `Research/sn9-gqa-kernel-lab` (Metal
kernels, bridge ABI 2, `-fmetal-math-mode=relaxed`):
- stage P and dS through threadgroup memory;
- keep the fp32 O for the backward pass's D term;
- skip fully masked key tiles.

**The v2 runtime:**
- loads the kernel only when the machine matches an entry of the allowlist named
  by `STRATA_SN9_TENSOROPS_ALLOWLIST` (chip, macOS build, torch, both asset
  hashes);
- self-tests forward and all gradients against an fp32 reference at first load;
- latches the kernel off for the life of the process on any failure, exception,
  non-finite result or shadow mismatch (`STRATA_SN9_TENSOROPS_SHADOW_EVERY`,
  default 500);
- journals `tensorops_selftest`, `tensorops_latched_off` and
  `tensorops_shadow_mismatch`;
- falls back to upstream SDPA, never grouped math, whenever the kernel declines.

**Qualified on:**

| Mac | macOS build | Speed, fwd+bwd attention with guards |
|---|---|---|
| M5 Pro | 26A428 and 26A434 | 4.0× upstream SDPA |
| M5 Max | 26A428 | 4.35× |
| M4 Max | 26A434 | qualified on a loaded host |

All passed every distribution, the 150-step training-equivalence test and
determinism checks. A whole transformer block is about 27–28 % faster on M5.
