1. Product and repository boundaries

Permanent requirements: native iOS/iPadOS/Android build readiness, excellent phone/tablet/widescreen UX, a course-agnostic core, a powerful public SDK, and in-product debug observability. Every release must preserve these properties.

The product's job is to improve demonstrated understanding over time. The supervisor owns a continuing teaching plan. The companion is its conversational interface. The course is a versioned, executable environment the supervisor can reshape. This is substantially more than a lesson player with question answering.

course-llms-and-modelsPrivateCurriculum, TAH material, examples, rubrics, labs and content tests. Uses released SDK packages and core interfaces.

Learner records belong in the private application database, not any Git repository. Private assets remain in private storage. Public CI never fetches the private course. Public examples use a small unrelated domain, such as algorithms and sorting; no fleet details, internal paths or incident data.

Hosting recommendation: a private authenticated web deployment with a persistent supervisor service, plus a documented self-host deployment. Local development remains supported. A sleeping laptop or suspended phone cannot provide always-on supervision; a hosted or continuously running self-hosted service can. No local GPU model is required.

The initial course is From dummy to professional: LLMs and models for an experienced systems engineer. Its final standard is independent competence demonstrated by code, explanations, experiments and incident analysis. Course completion is not a professional certification or a guarantee of production readiness.

2. Research, precedent and a stronger moat

The research register records 87 sources, their limitations and the decisions they inform. The strongest teaching direction is active practice, worked examples, retrieval and explanation, with assessment aligned to the actual capability being taught. IES; active-learning research; CMU alignment.

AI assistance can improve immediate performance without improving unaided understanding; separate the two in both UI and evidence. The relevant mathematics study does not establish an effect size for this adult engineering course. Primary study.

Editable learner models have a substantial research history. Personalized examples, multimodal content and AI tutoring also have existing precedents, including Learn Your Way and Khanmigo. Those features alone do not support a novelty claim.

Learning debugger

Treat a mistake as competing hypotheses: missing prerequisite, wrong mental model, typo or ambiguous assessment. Construct the smallest probe that distinguishes them, then teach the demonstrated gap.

Verified interactive teaching

A common computational model powers equations, code, visual state and test answers. The supervisor can generate new activities and prove key invariants before they teach the learner.

Longitudinal evidence

Record which intervention followed which evidence, then test transfer and retention. Improve teaching from outcomes rather than clicks or a model's confident assessment.

Learner-controlled continuity

Portable, inspectable history and profile; explicit course revisions; seamless agent handoff. Learner trust and a reusable author ecosystem are part of the product advantage.

The proposed moat is the reliable combination of these capabilities and a validated intervention/evaluation corpus. Open-source infrastructure can support an ecosystem and an excellent hosted service; it does not create exclusivity over an idea. Do not build a moat by trapping personal data.

Compare a curated fixed course, that course with contextual chat, and the full supervisor. Measure independent transfer, delayed retention, false mastery, time to useful intervention and learner control. A one-person POC supplies usability and case evidence, not a general causal efficacy claim. The latest reviewed September 2026 tutoring preprint is promising but preliminary and explicitly reports attrition. Study.

3. The learner's experience

  1. Orient and diagnose. Start with goals, known languages, available time and accessibility preferences. Sample ML understanding without forcing redundant programming lessons.
  2. Learn one mechanism. Move through intuition, exact behavior, equation, code and hardware implications as connected lenses.
  3. Predict and experiment. Predict before manipulating a model, tensor layout or pipeline event; reveal the real result and explain the discrepancy.
  4. Ask in context. Select a code line, formula, graph node or log entry; the companion sees the selection, current state and relevant history.
  5. Investigate confusion. The supervisor tests a teaching hypothesis instead of labeling every wrong answer a conceptual failure.
  6. Adapt the actual course. Insert a new example, simulation, lab, explanation or prerequisite episode; explain why and retain a return point.
  7. Check independently. Use a different problem family and a later revisit. Clearly distinguish assisted success, demonstration and retention.
  8. Resume anywhere. Preserve unfinished questions, code snapshots, episode revisions and profile overrides across sessions and tutor agents.

Initial episodes target 12–20 minutes as a product heuristic, not a universal optimal length. Longer labs span sessions. Revisiting prior material remains easy. Future preview access is configurable; credited advancement can be held by an explicit understanding gate, with visible requirements, help and appeal routes. Optional orientation and deeper mathematical/systems branches share the same capability map.

4. The persistent supervisor

A durable learner coordinator maintains the shared profile and goals; a child supervision workflow per enrollment handles course-scoped work. The coordinator resolves cross-course profile changes. Cross-course skill transfer requires an explicit concept mapping, not a matching word. Each enrollment workflow reacts to meaningful events and scheduled reviews. “Always on” means available and recoverable while the service is healthy and the enrollment policy permits the requested action; it does not mean an LLM continuously burns tokens while idle.

All retained history is accessible through authorized retrieval; it is not all pasted into every prompt. Assemble current authoritative state, a source-linked summary, concept-related evidence and relevant turns within a budget. Source events resolve summary conflicts. Platform/app versions, renderer capabilities and sync state accompany the context capsule without changing the learning objective. Show “Context used” and let the learner correct it.

A chat request waits for a specified event cursor or carries an explicit uncommitted view snapshot. Responses echo their context revision. Switching episodes during generation leaves the answer attached to its original episode and offers to follow the new one; it never silently relabels an old answer.

External agents use scoped MCP/HTTP tools such as get_context, get_profile, get_evidence, get_history and propose_intervention. The same authorization and grading rules apply. This Codex chat does not automatically inherit browser state; the implemented bridge and learner authorization make that possible. Built-in chat is the first guaranteed path.

Companion states are truthful: available, responding, building, waiting for input, provider unavailable or offline. Questions persist during outages. Server supervision can continue when the browser closes, subject to course caps, extension policy, budget and notifications. At closure it preserves context but stops further required expansion.

7. Dynamic content and executable teaching contracts

The supervisor can author whole remedial episodes, new simulations, code exercises, examples, tests and advanced branches. Its planning graph contains concepts, prerequisites, objectives and evidence links. Chapters organize navigation; episodes teach; activities generate evidence.

Need + evidence → intervention specification → artifact generation
 → schema/coverage checks → reference and negative tests → accessibility
 → review when required → personal course revision → delivery
 → transfer check → intervention outcome

Base course plus personal branch: immutable published releases; content-addressed personal revisions. Every patch identifies its parent, affected concepts, rationale, assets, tests, sources, validation report and rollback target. Apply at a safe boundary or as a clearly marked insertion. Preserve the learner's code and place.

Common model for multiple representations: for a gradient lesson, one tested computational graph produces visual values, formula annotations, trace tables and deterministic answers. Changing inputs changes them together. Authoring checks detect divergence. This is a major SDK capability: declare invariants, reference computations, permitted interactions and evidence emitted by an activity.

Prefer declarative registered simulators. When a new component is needed, the builder works in an isolated workspace, compiles/tests it, captures a preview, checks accessibility and resource limits, and publishes an immutable private sandboxed plugin. Generated code never runs in the authenticated parent application origin.

Verified routine material can auto-apply under learner policy. Unverified explanation is marked and cannot create mastery credit. New high-impact rubrics, removal of required objectives and ambiguous answer keys require review. Model agreement alone is not independent validation. Tests must accept valid variants and reject realistic wrong ones.

Old attempts keep their exact item/rubric versions. Fixing a defective question invalidates affected evidence with a reason and offers a replacement check; it does not rewrite an answer. Personal changes are visible, undoable and source-linked.

8. Assess understanding, transfer and retention

Use prediction, numeric calculation, trace annotation, code repair, counterexample construction, experiment design and teach-back. Multiple choice is valuable for a diagnostic probe, but cannot establish the entire skill.

Initial transparent policy: “demonstrated” needs independent success in two item families, including an application/transfer task, with no unresolved critical misconception. “Retained” adds a delayed independent check. These are configurable starting heuristics to validate in the pilot, not universal scientific thresholds.

Reattempts of the same item are not independent evidence. Hints and answer reveals are recorded; later novel tasks can demonstrate understanding. Optional confidence helps choose probes, but alone neither passes nor fails a concept. “I don't know” is useful evidence, without punishment.

Uncertain or disputed judgments schedule clarification and cannot silently establish deficiency. Record observable rubric reasons, not hidden reasoning. Generated assessment keys need independent validation. Browser-local assessments are learning tools; they cannot be advertised as tamper-resistant certification.

Initial spaced-review intervals might be 1, 3, 7 and 21 days, adjusted to observed evidence and availability; these are product defaults. Avoid uncalibrated mastery percentages. A later knowledge-tracing model must outperform this transparent baseline on held-out outcomes.

8A. Bounded adaptation, deadlines and extension allowances

New mandatory core capability: a course must have a declared completion/expansion policy. Default to bounded progression. Open-ended learning is an explicit opt-in mode, available only where the course owner permits it. The supervisor may teach indefinitely in that mode, but individual jobs, spending and safety limits remain bounded.

The distinction is grounded in existing LMS practice: Open edX separates suggested pacing and course end dates; Canvas separates due and availability dates; Moodle separates completion reporting and access restriction. Our addition is an enforceable limit on the adaptive supervisor's own expansion of required work.

Finite by default even without a date: a fixed core objective set plus a finite remediation envelope prevents endless addition of requirements. Example author presets can combine 30 calendar days, a required-work allowance and two remediation cycles per concept. Numbers are illustrative and must be configured for the actual course. A publish-time validator rejects a nominally bounded policy with no terminating condition. Private POC cap values remain undecided; 56 episodes alone are not permission to add unlimited mandatory detours.

Policy hierarchy and time semantics

Resolve organization ceilings → course/run policy → enrollment/cohort override → chapter → episode/activity. Ordinary child settings may tighten a cap, not weaken an ancestor. An authorized override or grant changes a named policy level explicitly; it is never inferred from the most permissive field. The effective hard deadline is the earliest applicable adjusted hard deadline, and every applicable quota must have room. The UI and tools receive an explanation of the binding constraint.

Store UTC instants plus the authoring IANA time zone and original calendar rule. Calendar days are not silently converted into 24-hour durations. Daylight-saving gaps/ambiguities require an explicit resolved preview, then persistence of the accepted instant; device time-zone changes do not move deadlines. Server time governs acceptance. Anchors do not reset on refresh, course revisions, agent handoff, repeat attempts or renamed/generated episodes.

Policies state whether a relative duration pauses during an approved leave; an absolute deadline never moves implicitly. Idle browser time does not consume a study-effort budget. Planned required minutes are estimates used to control assigned work, not a stopwatch or reliable measure of cognitive effort. Display the estimate and uncertainty; never penalize a slower reader. Outages/accommodations are explicit audited adjustments, separate from discretionary extension pools. Apply WCAG timing requirements to applicable interactive limits rather than treating a business deadline as permission for an inaccessible interface.

Supervisor behavior inside a finite envelope

  1. Before enrolling or publishing a new required path, compare core work and prerequisite needs with the declared envelope. Flag infeasibility; do not promise a complete 50-hour course in a 5-hour budget.
  2. Give the supervisor a resolved constraint snapshot on every turn: deadline, remaining quotas, extension policy, policy revision and binding scope. The companion displays the same values.
  3. Reserve room for core objectives and final assessment before adding enrichment. Near a cap, prefer a small diagnostic, alternate explanation, replacement or removal of optional work over accumulating extra requirements.
  4. If the plan no longer fits, show the tradeoff: continue within the current limit with documented gaps, request an allowed extension, or make an explicit goal/scope change. The supervisor cannot silently weaken pass criteria.
  5. Bound repeated intervention cycles and stop a failing strategy. The learner can request more practice when policy permits; more attempts are not automatically more learning.
  6. Maintain stable core coverage. Personal extras have a separate counter so adding a remedial example does not move a displayed completion denominator indefinitely.

Extensions are explicit, optional and metered

Each policy can disable extensions or define an allowance: total days/minutes/additional activities, maximum number of grants, maximum per grant, permitted scopes, shared versus scope-specific pools, approval authority and any ultimate hard ceiling. Units and charging rules must be named. An extension day for a chapter is not automatically a day added to the course end date.

A supervisor offer includes: why the extra work is useful, proposed work, added time/scope, current and proposed effective deadline, exact allowance cost, balance before/after, parent constraints, effect on the rest of the plan, and alternatives. It asks for the learner's affirmative acceptance. Silence, continued studying, or a previous extension is not consent for another one. Declining consumes nothing and does not trigger repeated pressure; use a cooldown and offer-frequency budget.

Example: “Add 2 days to this chapter to practice gradient accumulation. This uses 2 of the 5 days remaining in your shared chapter-extension allowance; 3 remain. The course still ends on 30 November at 18:00 in its configured time zone. You can instead continue now and keep this concept marked for review.” Dates and quantities are sample policy values, not a schedule assigned to you.

Only offer a grant that changes the effective constraint. If the parent course ends tomorrow, a two-day child extension must be clipped with clear consent, bundled with a separately authorized parent extension, or rejected. A grant that increases a deadline does not silently increase activity/compute budgets.

State machine: proposed → accepted/pending-admin → granted, or declined/expired/rejected/superseded. Acceptance is revalidated against current policy, balance and time. Grant + allowance debit + schedule revision + audit event commit atomically using an idempotency key. Two agents or devices cannot spend the same final allowance. Proposal does not consume allowance; acceptance after balance changes must show revised terms. Refunds, revocations and exceptional grants are separate audited operations; deleting a grant cannot erase usage.

Changing a course template does not refill existing allowance ledgers. Grants preserve their provenance. Admin changes to existing enrollments require an impact preview; reducing a deadline cannot silently revoke already promised time. Discretionary allowance and legally/operationally required accommodations are separate. Any paid extension would need separate explicit commercial consent; no billing mechanism is assumed.

Enforcement and the end of a course

A server-side policy service gates planning, job admission, tool calls and artifact publication. The LLM cannot bypass a cap by calling a tool directly, generating a child course or relabeling required material as optional. New enrollments/continuation branches require explicit authority. Required-work reservations are acquired atomically across applicable scopes; cancellation releases only unused reservations. Durably record introduced/assigned work so churn cannot reset the allowance.

Durable timers wake the supervisor at boundaries, but commit-time checks remain authoritative if timers fire late. A worker started before the cap cannot publish afterward without a still-valid policy or defined grace. Fence stale jobs with the current policy revision. Request cancellation and bound cleanup; preserve learner drafts. Separate technical grading of an on-time submitted attempt from new learning activity: grading may finish after the cutoff without extending the course.

Track orthogonal outcomes: course coverage, mastery evidence, and enrollment/access state. Examples: “completed and demonstrated,” “course ended with gaps,” “paused,” or “continuing under an approved extension.” At the cap, produce a final evidence report, retain achieved work and unresolved concepts, and stop mandatory expansion. Existing-material reading remains available by default, subject to the course's explicit access policy. Optional ongoing maintenance/review is a separate opt-in track and never silently reopens a completed course.

8B. Optional placement tests and evidence-based skipping

Admin-controlled, learner-optional feature: the course owner can enable a placement test and define what it may exempt. When enabled, onboarding offers “Start from the beginning” as the normal route and a clearly optional “Find my starting point.” Declining or stopping placement does not block enrollment or penalize the learner.

Duolingo provides a relevant precedent for adaptive placement and partial-credit scoring, while also describing the limits of arbitrarily chosen scoring values. Our placement engine must be calibrated against its own objectives and learners; it does not inherit another product's psychometric validity. Technical account.

Interrupted/offline placement resumes from an authoritative receipt. Partial tests leave uncovered concepts unknown, not mastered. Failed provider evaluation is a pending technical state, not a wrong answer. Placement respects course caps and its own budget; its clock anchor and effect on course timing are shown before starting. Large fonts, assistive technology or slower reading are not treated as lower ability.

Admin/debug views expose which evidence caused each exemption, why another unit was retained, the item/rubric/policy versions and any human override. Test guessing, confident errors, partial credit, uneven strengths, hidden prerequisite gaps, answer help, repeated exposure, retests, outdated evidence, interrupted sync and appeals. Track false-skip and unnecessary-repetition rates in the pilot.

Responsive and adaptive behavior

Use effective window width, available height, safe areas, input mode and text size—not device brand detection. Proposed compact/medium/expanded starting classes are below 600, 600–839 and 840+ logical pixels, refined by content tests. iPad split view can be compact; a landscape phone is not automatically a desktop. Android guidance emphasizes available window space and Flutter distinguishes fitting layout from usable interaction. Android; adaptive principles.

  • Phones: one central required activity, a clear next action above the safe area/keyboard, companion as a contextual sheet or full-screen conversation, optional tracking under a secondary menu. Opening help never loses the answer or position.
  • Tablets: readable lesson pane plus companion when space permits; collapsible panes in portrait/split view; stylus, hardware keyboard, touch and pointer supported. No stretched phone layout.
  • Widescreen desktop: constrain reading width; use remaining space for companion and, only in authorized debug mode, an inspector. Avoid spreading one paragraph across the screen.
  • Accessibility: Dynamic Type/font scaling, VoiceOver/TalkBack, web screen readers, keyboard/switch controls, reduced motion, text equivalents, no hover-only actions, and touch targets meeting platform guidance (44pt iOS/48dp Android design targets).
  • Input/lifecycle: software keyboard, composition/IME, focus restoration, native back gestures, safe areas, rotation, resize, background/resume, process death, low-memory conditions, slow networks and interrupted uploads.

Explicitly enable and test iPad support; it is not inferred from a successful iPhone build. Maintain portrait/landscape and resizable-window support unless a particular activity has a justified, accessible alternative. Expo tablet setting; native accessibility.

15. The actual TAH case, taught accurately

TAH is the consumer Train at Home application connecting to Macrocosmos's IOTA distributed training system on Bittensor SN9. Separate official high-level documentation, the architecture paper, pinned upstream code, our patched runtime and research candidates. Some paper features are proposals rather than deployed protocol. TAH guide; IOTA primer.

The inspected split implementation has a first partition with token embeddings and transformer blocks, middle partitions processing activations, and a final partition with remaining blocks, normalization and a vocabulary projection. The training runtime computes loss and propagates gradients. L0/L1/L2 are pipeline partitions containing multiple model operations/blocks, not three neurons or three attention heads.

Our four Macs are peers in shared runs, not a permanently wired private three-machine pipeline. Each assigned worker holds its split's local model and optimizer state. Show forward activation traffic, backward activation-gradient traffic and epoch update/merge traffic separately. Teach the general meaning of an epoch, then distinguish IOTA's orchestrated phase boundaries from a conventional full dataset pass.

On each Mac, the official application/control host, STRATA supervisor/relay and Python worker have distinct roles. PyTorch dispatches operations through MPS/Metal to the GPU. MLX is a different framework, not a PyTorch toggle. GPU neural accelerators and the separate Apple Neural Engine are different hardware. Unified memory helps fit workloads but is shared, bandwidth-limited and vulnerable to pressure; Macs are suitable here without being universally superior training hardware.

The private incident investigation reproduced a systematic M5 layout incompatibility in chained tensor matrix operations, producing wrong forward output and some wrong gradients. 16. A complete adaptive episode

Topic: backward calculates gradients; the optimizer changes parameters. Use prediction = w × x + b and loss = ½(prediction − target)². With x=2, w=0.5, b=0 and target=3, forward gives prediction=1 and loss=2. Backward gives dL/dw=−4 and dL/db=−2 while w and b stay unchanged. With learning rate 0.1, the update gives w=0.9, b=0.2. A fresh forward gives prediction=2 and loss=0.5.

Separate Forward, Backward and Update controls synchronize numbers, code highlighting and a graph. Ask what changes after backward but before the optimizer. A wrong answer triggers a discriminating probe, not immediate diagnosis.

If evidence supports confusion about mutation, generate a personal episode comparing parameter buffers and gradient buffers. Include two backward calls before one update, an executable trace and a memory diagram. Validate against a scalar oracle and trusted autograd; wrong accumulation and wrong-sign implementations must fail.

Then ask a novel transfer question: what must a middle TAH split receive from a downstream split to compute gradients, and does message receipt itself update its weights? Store the answer and assistance state; revisit later. The learner can inspect why the detour exists, edit the hypothesis, ask for another explanation or return to the original path.

Framework callbacks feed OpenTelemetry; stable domain records supply learning semantics the framework cannot know. AI SDK telemetry; OpenTelemetry conventions.

Decision transparency: show actual inputs, outputs, evidence, rule evaluation and a concise decision explanation. Do not invent or expose hidden model chain-of-thought. If a provider does not supply a metric, label it unavailable rather than zero. Distinguish estimated cost from billed usage, a queued task from active execution, and a model suggestion from a committed state transition.

Privacy and authorization: debug mode is an authorized server capability, not a query-string switch. Learners can inspect their own learning explanations; course admins/developers receive only permitted scopes and fields. Default broad telemetry disables raw input/output capture. Sensitive payload viewing requires explicit scoped access, redaction, retention and an audit receipt. Never log credentials. The AI SDK documents input/output capture defaults, so configure them deliberately and test with canary secrets.

Reliability: learning decisions, grades, grants and publication receipts are transactionally recorded domain events even if telemetry is sampled. Model traces may be sampled/retained under policy. An unavailable collector cannot make a trace look complete; show missing spans and bound local buffers. Audit-critical writes fail safely if their required durable receipt cannot be committed.

Safe controls: read-only inspection by default. Retry, cancel, regrade, re-run tool and replay are separate scoped actions. Replays use frozen inputs in a sandbox, cannot re-send external effects or mutate real learner progress, and record new run IDs. A real correction requires an authorized domain command and preserves the original evidence.

Own the essential inspector in core so no commercial observability tier is required. Optional self-hosted Langfuse MIT-core integration can provide further model analysis. Do not depend on its enterprise RBAC/SSO features to enforce our access boundaries.
