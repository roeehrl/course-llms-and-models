**What is solid:**
- Evidence integrity: only 3 code paths write evidence, and none of them is driven by a model.
- Idempotent receipts, and the transactional extension ledger tested with real Postgres races.
- The pure policy domain (`packages/policy`).
- Server-side gate re-check, and the Docker sandbox.
- Temporal recovery for each job.
- Learner-profile override precedence.
- Visual/media playback never grants credit.
- Release byte-identity checks.

**What is weak:**
- The supervisor "learning debugger": there are no teaching hypotheses, probes or trigger table.
- There is no GateDecision entity.
- Context capsule, debug and observability: no OpenTelemetry, no correlation, no safe replay.
- The SDK surface: only 3 of the 26 `define*` functions exist, and the CLI has only `validate` and `compile`.
- No activity runtime: core refuses every `activity` block at publish.
- No media-generation job service.
- Admin areas: Overview, Placement, AI-supervision controls, Audit and View-as-learner are missing.
- No nightly CI, SBOM, agent evals or threat model.

## Problems found outside the requirements (fix first)

1. **Wake-up scan bug.** `core:services/api/src/wakeups.ts:33-34` uses `ORDER BY e.id LIMIT 200` with no cursor. Enrollments beyond the first 200 active ones never get deadline warnings or automatic closure at the cap. Only the course scope is scanned, and closure errors are swallowed (`wakeups.ts:42`).
2. **Placement treats "pending" as wrong.** A rubric attempt in `pending_review` has `passed:false` (`server.ts:352`). `placementPlan` reads that as a failure (`placement.ts:105,157`). This violates U05: a provider failure must not count as a wrong answer.
3. **Conversational gate can never be published.** The SDK accepts `conversationalEvaluatorId` and skips family checks for it (`sdk:src/validate.ts:114-116`). Core refuses it at publish (`publication.ts:66`, `PUBLISH_EVALUATOR_RUNTIME_UNAVAILABLE`).
4. **Activity blocks can never be published.** Core refuses every `activity` block (`publication.ts:46`, `PUBLISH_ACTIVITY_RUNTIME_UNAVAILABLE`). Activity completion also requires evidence that cannot be produced (`server.ts:392`).
5. **CI.**
   - Private course CI has had 0 successful runs in its last 60. GitHub reports failed account payments or the spending limit (run 38644974881).
   - Core `main` CI is red on the latest push (run 38605637649, the Browser/learner job).
   - `scripts/release-artifacts.mjs:194` accepts `skipped` steps, so a critical skip does not fail a release.
   - `deploy/local/backup.test.mjs:57` skips silently in CI.
6. **Private workspace name in a public test.** The private workspace name appears in public core test `services/api/test/password-auth.integration.test.ts:332`. Rename it to something neutral.
7. **Stale version claims.** `core:README.md:84` and `sdk:README.md:5` claim SDK 0.2.0, but the packages pin 0.4.0. No supported SDK range is declared anywhere.

### #47 design requirements: Core upgrade without breaking installed courses

The operator can see that a newer Core release exists and upgrade the pilot from the admin. The upgrade must be refused if it would stop any installed course from working.

1. **Discovery.** "Core update available" from the public Core GitHub releases (same allowlisted fetcher as #46), showing version, release notes, prerelease flag and the published manifest digest. Off by default beyond a manual "Check"; automatic upgrade is never the default.
2. **Candidate verification before anything changes.** Download into a new release root, verify SHA256SUMS, the release manifest identity (tag object, commit, run) and every asset, exactly as the coordinator's install script does today. Temporal and other host binaries are copied from the running root only when byte-identical requirements allow it.
3. **Compatibility gate (the core requirement).** For every course release that is published, selected for new learners, or pinned by any non-terminal enrollment (active, paused, closed with open reviews, etc.), the candidate Core must prove it can still run it:
   - the course's `sdkVersion` is inside the candidate Core's supported SDK range;
   - the course's `minimumCoreVersion` is satisfied;
   - the candidate's own publication/runnable checks (`prepareCourseRunnable`/`assertCourseRunnable`, activity runtimes, evaluators, extensions, adaptation adapters, host requirements such as code fixtures and teaching verifiers, recovery registries) pass for that exact stored bundle digest, run by the candidate code against a read-only copy;
   - the migration rehearsal on a fresh copy of the live database applies cleanly and leaves enrollment pins, evidence and receipts unchanged (the coordinator's current rehearsal, automated);
   - the candidate's adapter digests match what installed courses were approved against, or the change is listed as requiring re-approval.
   Any failure blocks the upgrade and the admin shows which course/version/enrollment count is affected and why, with the fix (update the course first, install a missing host requirement, or wait for a Core release that supports it). There is no override that upgrades anyway while active learners are pinned to an incompatible course; at most an owner can archive the affected release first, which itself requires no non-terminal enrollments on it.
4. **Courses ahead of Core and Core ahead of courses.** Courses declare the SDK range they were built for; Core declares the SDK range it runs. Both directions are checked, so a Core that drops an old SDK major is blocked while any pinned course still uses it.
5. **Execution.** The existing `deploy/local/upgrade.mjs` path: stop, backup, restore drill, start new root, health, automatic rollback on failure. Triggered from the admin only by an owner, with a typed confirmation of the version, and only when no supervisor job is mid-flight (or after a drain with a deadline). The running API never replaces itself in place; a separate host-side upgrader process performs it, and the admin shows its progress and result.
6. **After upgrade.** Re-run the compatibility checks on the live system and a smoke acceptance; on failure, roll back to the previous root and backup automatically and report.
7. **Audit and evidence.** Every check, refusal, upgrade and rollback is audit-logged with versions and digests.
8. **Acceptance.** Tests with a synthetic course pinned to an SDK the candidate no longer supports (blocked), a course missing a host requirement in the candidate (blocked), a compatible set (upgrades and passes smoke), a failing post-upgrade smoke (rolls back), and a mid-flight job (drains or refuses).
